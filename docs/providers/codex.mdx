The local patches remain separate from upstream releases.

## Authorization and deployment limits

The implementation uses the device flow from the official Codex CLI.
OpenAI documents this flow for Codex, not as a public hosted-gateway OAuth contract.
An eligible subscription and enabled device authorization are required.
Organization administrators can restrict device authorization.
The mock tests do not establish OpenAI permission, live compatibility, or Amp client compatibility.

Use only your authorized account and permitted workload.
Do not share personal credentials, evade subscription limits, or present this integration as OpenAI-endorsed.
Review [Codex authentication](https://developers.openai.com/codex/auth) and [OpenAI terms](https://openai.com/policies/terms-of-use/) before deployment.
For shared or commercial hosting, establish permission separately.

## Build and start a local deployment

Requirements: Go 1.27.1, Node.js with npm, a C compiler, and a supported native Go plugin platform.

From the repository root, run:

```sh
make setup-workspace
go work use ./integrations/headroom
npm --prefix ui ci
npm --prefix ui run build
go build -o /tmp/bifrost-codex ./transports/bifrost-http
mkdir -p /tmp/bifrost-codex-config
cp tests/codex/config.example.json /tmp/bifrost-codex-config/config.json
export BIFROST_ENCRYPTION_KEY="$(openssl rand -hex 32)"
export CODEX_GATEWAY_KEY="sk-bf-$(openssl rand -hex 32)"
/tmp/bifrost-codex -app-dir /tmp/bifrost-codex-config -host 127.0.0.1 -port 8080
```

Keep both secrets in a secret manager for persistent deployments.
Do not regenerate the encryption key on restart.
The example binds only to loopback and stores the SQLite database in the working directory.
For network access, configure TLS and Bifrost management authentication first.
For multiple replicas, use a shared PostgreSQL config store and the same encryption secret.
Separate SQLite files do not coordinate replicas.

1. Open the gateway dashboard and select **Providers → Codex**.
2. Enter the gateway virtual key in the password field.
3. Start device authorization.
4. Open the displayed OpenAI authorization link in your own browser.
5. Enter the displayed device code on OpenAI, then authorize your account.
6. Wait for the dashboard to show **connected**.

Never paste OpenAI access tokens, refresh tokens, or device codes into a support conversation.
The dashboard keeps the virtual key in component memory, not browser storage.
A page reload requires the key again.

From another shell with the gateway key, run:

```sh
curl http://127.0.0.1:8080/v1/models?provider=codex \
  -H "x-bf-vk: $CODEX_GATEWAY_KEY"
curl http://127.0.0.1:8080/v1/responses \
  -H "x-bf-vk: $CODEX_GATEWAY_KEY" -H 'Content-Type: application/json' \
  -d '{"model":"codex/gpt-5.3-codex","input":"Reply with OK","stream":true}'
```

Use a model returned by your account catalog if the example model is unavailable.
OpenAI-compatible clients use the gateway `/v1` base URL, a gateway virtual key, and a `codex/` model prefix.
For clients that omit provider prefixes, configure a Bifrost routing rule rather than forwarding an OpenAI bearer token.

## Protocol contract

Typed `/v1/responses` and `/v1/chat/completions` support unary and SSE output, function tools, reasoning, usage, and structured-output parameters.
Chat requests convert to Responses requests.
The upstream always streams with `store=false`; the provider collects terminal output for unary callers.
Opaque Responses passthrough preserves unknown JSON fields and SSE bytes through the existing Bifrost passthrough route.
Use `/openai_passthrough/v1/responses` with `x-model-provider: codex`, `x-bf-vk`, and an unprefixed body model for that route.
Raw Chat bodies are rejected because safe conversion requires typed input.

Unsupported parameters fail explicitly: `temperature`, `top_p`, `max_output_tokens`, `previous_response_id`, persistent storage, background execution, and unsupported Chat-only parameters.
Unsupported operations include files, batches, embeddings, audio, and image generation.
Large-payload bypass mode is rejected.
Unary opaque responses have a 32 MiB limit.
Requests cannot override the upstream URL, provider type, account header, or bearer token.

The provider uses existing Bifrost cancellation, streaming hooks, retry policy, and accounting.
It does not replay emitted stream bytes or retry uncertain OAuth token exchanges.
Model discovery queries the authenticated account and filters results through its gateway grant.
It does not put one account's catalog into a global cache.
The built-in semantic cache bypasses Codex reads and writes because its shared keys do not establish subscription ownership.
Custom plugins are trusted gateway code and must preserve this boundary.

Usage counts come from provider responses.
Budget costs use matching OpenAI API reference prices when available, not measured subscription charges.
Unknown model pricing can produce unknown costs, so token limits remain necessary.
No savings claim follows from compression estimates or subscription usage.

## Ownership and credential lifecycle

Each active virtual-key database ID owns one connection in OSS.
A shared virtual key therefore shares its connection: issue separate virtual keys for separate users.
Dashboard authentication alone cannot select an owner.
Every management request also requires `x-bf-vk`.
An OpenAI JWT never grants gateway access.
Inference requires an admitted gateway grant and rechecks the virtual key in the database.
Provider routing, budgets, and access rules remain in the normal pipeline.

The config-store migration adds `codex_connections`.
Credentials use the established Argon2id-derived AES-256-GCM encryption implementation.
The encrypted envelope includes its owner and connection ID to reject ciphertext copied between rows.
No credentials appear in management responses, and upstream auth errors are sanitized.
Operators must also restrict database access, backups, logs, proxy access, and host memory access.

Database compare-and-swap coordinates polling and refresh across replicas.
Only one operation can exchange a rotating refresh token.
A crashed or uncertain exchange requires reconnect after its operation deadline, rather than reusing a possibly consumed token.
Transient contention returns an operation-in-progress error.
Reconnect creates a new connection ID, so stale operations cannot overwrite the replacement.

Disconnect deletes the local connection and prevents later credential resolution.
It does not revoke OpenAI sessions or cancel a request that already obtained its credential.
Use OpenAI account controls for remote session revocation.
Deleting or disabling a virtual key blocks later requests, but does not erase its encrypted connection automatically.

## Verification without credentials

From the repository root, run:

```sh
bash tests/codex/run.sh
```

The harness builds the gateway and Headroom plugin with the same dependency graph and toolchain.
It launches a disposable gateway against a local TLS fixture for OpenAI auth and inference.
Only that child process trusts the generated test CA.
No production endpoint override or personal credential is necessary.
The tests cover owner isolation, refresh rotation, token non-disclosure, cancellation, tools, streaming, and failure behavior.
The full-path test loads the native Headroom plugin with compression disabled.
It does not prove compression quality or real-provider behavior.

With the gateway running, run the isolated browser test:

```sh
npm --prefix tests/e2e ci
npm --prefix tests/e2e exec -- playwright install chromium
# Run in tests/e2e:
npx playwright test --config playwright.codex.config.ts
```

The browser test mocks onboarding responses and checks pending, connected, disconnected, and error states.
Provider-harness folder `104 - codex-oauth` adds opt-in live protocol cases.
Do not run live cases without account authorization and a usage limit.

The September 22, 2026 verification passed the offline harness, provider/lifecycle race tests, full config-store/governance/HTTP-handler/lib suites, and targeted Go vet.
The frontend build/typecheck, six API tests, and the browser contract test passed.
The full core test run was not green: MCP fixture servers were missing, and an SSRF TEST-NET reachability assumption failed in this orb.
Three OpenAPI invariant failures also reproduce on the unmodified imported baseline.
They concern logging fragments, a duplicate virtual-key rotation operation, and routing security declarations.

The binary vulnerability scan reports `GO-2026-6354` and `GO-2026-6355` in the pinned `golang.org/x/crypto v0.55.0` SSH code.
Both advisories list v0.56.0 as the fix.
These inherited dependencies remain unchanged in this patch, so this distribution is not security-clean.
The source scan stalled under memory pressure; the completed scan used `govulncheck -mode=binary`.

## Upgrade and rollback

1. Back up the config database and encryption secret before upgrade.
2. Stop traffic before the first migration.
3. Start one replica to apply the migration under the existing config-store migration lock.
4. Start the remaining replicas with the same encryption secret.
5. Rebuild native plugins with the final gateway toolchain and dependency graph.
6. Run the offline harness before restoring traffic.

For rollback, disconnect Codex accounts and remove the Codex provider before starting an older binary.
The additive table can remain unused, or a database administrator can remove it after backup.
Restore the pre-upgrade database if older migration code rejects the newer schema version.
Do not rotate the encryption secret without a separate data re-encryption procedure.
This patch does not add that procedure.

## Research and remaining limits

Sources reviewed include [Codex CLI](https://github.com/openai/codex), [LiteLLM](https://github.com/BerriAI/litellm), and [OpenCode](https://github.com/anomalyco/opencode).
The official CLI establishes the issuer, client ID, device endpoints, and refresh exchange.
This implementation replaces process-local credential files with owner-bound database records.
Bifrost [PR #7325](https://github.com/maximhq/bifrost/pull/7325) provides caller-token passthrough, not a credential lifecycle.
[PR #7393](https://github.com/maximhq/bifrost/pull/7393) supplies opaque passthrough safeguards.
[PR #2715](https://github.com/maximhq/bifrost/pull/2715) is not an implementation dependency.

Live device authorization, model availability, full Amp sessions, and provider terms acceptance still require an authorized operator.
Headroom limitations remain in `integrations/headroom/README.md`: CCR is disabled, strict learned-state isolation is unresolved, and internal retry costs are unknown.
Headroom metadata is per replica, and no real-provider answer-quality evaluation is included.
